enable = true
# Limits (optional). The values below are the defaults.
#max_depth            = 16   # max. JSON nesting depth (max. 32)

# Example: CLAT counters of Gluon nodes
[[respondd.metrics.rule]]
path        = "statistics.clat.{direction}"
measurement = "clat"

# Example: mesh VPN peers of Gluon nodes
[[respondd.metrics.rule]]
path        = "statistics.mesh_vpn.groups.{group}.peers.{peer}"
measurement = "mesh_vpn_peer"
values      = { method = { active = 1, standby = 0 } }

    Respondd data of a node (example):

    1

3

    {"statistics": {
  "clat": {"v4_to_v6": {"packets": 12, "bytes": 3400}, "v6_to_v4": {"packets": 10, "bytes": 2900}},
  "mesh_vpn": {"groups": {"muc01": {"peers": {"pgw01": {"established": 3600, "method": "active"}}}}}
}}

    Result (one point for each matched object):

    measurement tags fields
    clat nodeid, direction=v4_to_v6 packets=12, bytes=3400
    clat nodeid, direction=v6_to_v4 packets=10, bytes=2900
    mesh_vpn_peer nodeid, group=muc01, peer=pgw01 established=3600, method=1

    Each point also has the tags hostname, site and domain of the node, if known.

    Grafana query (InfluxQL). The query does not contain group or peer names:

    1
2
3
    SELECT last("established") FROM "mesh_vpn_peer"
WHERE "nodeid" =~ /^$node$/ AND $timeFilter
GROUP BY time($__interval), "group", "peer"

    Rules

    • path is a list of segments with a dot between them.
    • The first segment must be nodeinfo, statistics or neighbours.
    • A segment is a name (a-z, 0-9, _, -) or a capture {name}. A capture matches each key at this level. The key becomes the value of the tag name.
    • Use a capture for each key that the node sets (for example gateway or peer names). Then the field names stay the same for all nodes and queries can use GROUP BY.
    • measurement is the InfluxDB measurement (a-z, 0-9, _). You cannot use the built-in measurements (node, link, dhcp, global, firmware, model, autoupdater). You cannot use the built-in tags (nodeid, hostname, site, domain) as capture names.
    • fields (optional) is a list of paths below the match, for example ["v4_to_v6.bytes"]. Without fields, Yanic uses only the values directly below the match.
    • values (optional) changes strings to numbers, for each field.
    • Yanic does not use regular expressions, templates or other expressions. A wrong rule stops Yanic at start.

    Values

    • All fields are written as float.
    • Numbers: Yanic drops values that are not finite.
    • true and false: written as 1 and 0.
    • Strings: dropped. Exception: values has the field and the string.
    • Arrays and null: dropped. A point without fields is not written.

    Security

    Respondd data comes from the nodes. Yanic does not trust this data.

    • Field names come only from the config or from fixed keys below the match. Keys from a capture are only tag values. They are never field names.
    • A key from the node must have 1 to 64 characters from A-Z, a-z, 0-9, _, -. Yanic ignores other keys. Yanic compares names in lower case, with _ for -.
    • Yanic writes tags, fields and names only through the InfluxDB client library.
    • Yanic never changes built-in measurements, fields or tags.
    • If a limit is reached, Yanic stops reading or drops the point or field. The node data is still saved.
    • When max_tag_values or max_field_names is reached, Yanic drops new values and writes a warning. Known values continue to work.

    Info

    Yanic also drops respondd responses with more than 1 MiB of uncompressed data.

    [[database.connection.influxdb2]]

    Save collected data to InfluxDB2.

    There are the following measurements:

    • node: store node specific data i.e. clients memory, airtime
    • link: store link quality between two interfaces of two different nodes (tq for Batman IV, throughput for Batman V) with i.e. nodeid, address, hostname
    • global: store global data, i.e. count of clients and nodes
    • firmware: store the count of nodes tagged with firmware
    • model: store the count of nodes tagged with hardware model
    • autoupdater: store the count of autoupdate branch

    Info

    A bucket has to be set in buckets and buchet_default otherwise yanic would panic.

    Warning

    yanic does NOT prune node's data (so please set up data retention in InfluxDB2 setup).

    We highly recommend to setup e.g. Data retention in your InfluxDB2 server per measurements.

    [[database.connection.respondd]]

    Forward collected respondd package to a address (e.g. to another respondd collector like a central yanic instance or hopglass)

    Yanic sends each section (nodeinfo, statistics, neighbours) as it was received. Keys that Yanic does not know (for example statistics.clat) stay in the data, so the receiving Yanic can use them in [respondd.custom_field] and [respondd.metrics]. A section from the state file (before the first response after a start) is sent with known keys only.

    2. Destination address to connect/send respondd package.
